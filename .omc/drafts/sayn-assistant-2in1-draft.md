# План: Sayn — голосовой ассистент 2-в-1 (черновик Planner)

Источник требований: `.omc/specs/deep-interview-sayn-assistant-2in1.md` (ambiguity 20%, PASSED).
Режим: RALPLAN-DR **deliberate** (миграция данных по проду, мультитенантность, ПДн детей).
Статус: **pending approval**.

---

## RALPLAN-DR

### Принципы

1. **Одна дверь для доступа.** `src/middleware.ts:1` уже объявляет себя единственным
   местом контроля доступа. Мультитенантность обязана усилить это правило, а не
   завести второй экземпляр проверок.
2. **Одна дверь для перехода состояния.** Действие доступно из бота и из mini-app;
   значит переход обязан существовать ровно в одной функции, а уведомления —
   быть её следствием, а не обязанностью вызывающего.
3. **Ломающее — до первого клиента.** `task_assignees`, `kind` и `org_id` меняют форму
   чтения. После второго тенанта их стоимость умножается на число арендаторов.
4. **Изоляция доказывается тестом, а не намерением.** Уже есть `test/access.test.ts`
   (677 строк) — расширяем его, а не заводим отдельный ритуал.
5. **Прод не останавливается.** `sayn.alrevion.com` работает; каждый шаг обязан быть
   развёртываемым сам по себе.

### Драйверы решения (топ-3)

1. **Риск межтенантной утечки.** В задачах будут фамилии учеников; у команды уже есть
   доказанная утечка между кабинетами в Stomiko. Это доминирующий драйвер.
2. **Стоимость переделки формы данных.** `responsible_user_id` — единственное поле,
   от которого зависят ~8 мест кода и все три cron-запроса.
3. **Скорость до живой проверки речи.** Личный слой нужен на руках через недели, а не
   месяцы: он поставляет живые фразы для отладки разбора до школы.

### Варианты последовательности

**Вариант A — «org_id первым».**
Сначала арендаторы и тест изоляции, потом адресаты, потом `kind`.
*За:* тест изоляции пишется против неподвижной цели и становится зелёным до того, как
модель начнёт меняться; самый ранний срез риска №1.
*Против:* каждый роут правится дважды — сначала на `org_id`, потом на `task_assignees`.

**Вариант B — «task_assignees первым».**
Сначала форма адресатов, потом `kind`, потом арендаторы.
*За:* роуты переписываются один раз, в новую форму сразу с `org_id`.
*Против:* тест изоляции пишется последним, то есть риск №1 живёт дольше всего; и
пишется он против кода, который только что весь переписали — худший момент.

**Вариант C — «сначала запечатать протечки, потом всё остальное» (предлагается).**
Шаг 0: закрыть четыре неограниченных места чтения (`routes.ts:194`, `229`, `299`,
`608–627`) **до** введения `org_id` — просто как правильную область видимости внутри
одной организации. Затем `org_id` + тест изоляции. Затем `task_assignees` + `kind`
одной миграцией.
*За:* риск №1 срезается первым и без ломающей миграции; `attachmentForAccess`
схлопывается в `requireProjectAccess` до того, как появится второй экземпляр правил;
адресаты и `kind` едут вместе, потому что `kind` без адресатов бессмыслен.
*Против:* шаг 0 не даёт видимой пользователю функциональности — его придётся защищать
перед самим собой.

**Отклонение альтернатив:** вариант B отклонён драйвером №1 — он оставляет
доказанный класс ошибки открытым дольше всех при том, что цена ошибки здесь —
персональные данные детей. Вариант A поглощён вариантом C, который отличается только
тем, что дешёвая часть работы делается до дорогой.

## Пре-мортем (3 сценария провала)

**Сценарий 1. Утечка приезжает через справочник людей, а не через задачи.**
Вторую школу завели, тест изоляции зелёный — потому что он проверял роуты задач и
проектов. А `GET /users` (`routes.ts:194`) отдаёт весь `users` без условий, и директор
школы А видит поимённый список сотрудников школы Б. Обнаруживается не тестом, а
клиентом.
*Противоядие:* тест изоляции строится не как список проверенных роутов, а как
**перебор всех зарегистрированных роутов Hono** — новый роут без области видимости
роняет CI по умолчанию, а не по забывчивости автора теста.

**Сценарий 2. Двойное закрытие.** Задачу закрыли из mini-app; cron
(`scheduled.ts:34-57`) всё ещё видит её как `in_progress`, потому что переход
обновил не то поле, и присылает «ВЫ ПРОСРОЧИЛИ ДЕДЛАЙН» по сделанной работе. Директор
теряет доверие к напоминаниям на второй день — а это, по спеке, и есть продукт.
*Противоядие:* переход состояния существует в одной функции; ни один роут не пишет
`status` напрямую. Тест: закрытие каждым из двух путей приводит систему в
побитово одинаковое состояние.

**Сценарий 3. Миграция `responsible_user_id` → `task_assignees` теряет исполнителей.**
`wrangler d1 migrations apply` — форвард-онли, автоматического отката нет. Бэкфилл
отработал частично (или отработал, но код ещё читает старое поле), и часть задач
остаётся без адресата: они пропадают из «Моё» у людей и из cron-выборок, потому что
все три запроса в `scheduled.ts` используют `JOIN users u ON u.id = t.responsible_user_id`
— внутренний JOIN молча выбрасывает строки без совпадения.
*Противоядие:* expand/contract. Старое поле не удаляется в том же релизе; пишем в оба;
инвариант «`COUNT(*) FROM tasks` = `COUNT(DISTINCT task_id) FROM task_assignees`»
проверяется миграционным тестом и разовым запросом на проде до переключения чтений.

## Шаги реализации

### Шаг 0 — запечатать области видимости (без миграций, деплоится сам по себе)

- `src/routes.ts:194-202` — `GET /users` получает область видимости. Сегодня в пределах
  организации-по-умолчанию; после шага 2 — по `org_id`.
- `src/routes.ts:229-232` — `GET /projects/archived` то же самое.
- `src/routes.ts:299-306` — `GET /archive/mine`: `responsible_user_id = ?` переживёт
  шаг 3 как чтение из `task_assignees`, поэтому помечается как точка последующей правки.
- `src/routes.ts:608-627` — `attachmentForAccess` схлопывается в вызов той же логики,
  что и `requireProjectAccess` (`src/middleware.ts:37-65`). Комментарий на
  `routes.ts:604-607` сам признаёт, что это ручное зеркало; второй экземпляр правил
  доступа не должен дожить до мультитенантности.
- Тест: расширение `test/access.test.ts` — перебор роутов, а не список.

**Приёмка шага 0:** ни один роут не выполняет чтение таблиц `users`, `projects`,
`tasks`, `attachments` без ограничения по видимости вызывающего; тест-перебор роутов
падает при добавлении роута без ограничения.

### Шаг 1 — единая точка перехода состояния (без миграций)

- Ввести одну функцию перехода задачи, через которую обязаны идти
  `routes.ts:493-528` (move), `531-538` (archive), `541-550` (restore),
  `555-568` (confirm), `572-589` (reject) и весь `scheduled.ts`.
- Уведомления (`notifyTask`, `routes.ts:30-45`) становятся следствием перехода.
- **Вебхуков не появляется.** Спека требует их, чтобы бот узнавал об изменениях из
  mini-app; но оба клиента бьют в один Worker (`src/index.ts:10-12`), поэтому
  внешний HTTP-callback был бы обходом собственного процесса. См. ADR-2.

**Приёмка шага 1:** закрытие задачи из бота и из mini-app приводит к одинаковым
`tasks`-строке и множеству `events`; после закрытия ни одна ветка `scheduled.ts` не
отправляет по ней сообщений.

### Шаг 2 — организации и тест изоляции (ломающая миграция №1)

- `orgs`; `org_id` на `users`, `projects`, `groups`, `tasks`, `events`, `attachments`.
- Бэкфилл: всё существующее — в одну организацию.
- `org_id` попадает в `SessionPayload` (`src/types.ts:78-82`) и проверяется в
  `src/middleware.ts` наравне с ролью.
- `mcp.ts` — `MCP_USER_ID` (`wrangler.jsonc`) становится привязкой к организации;
  хардкод одного идентификатора при нескольких арендаторах — дыра в границе.

**Приёмка шага 2:** автотест перебором роутов с токеном организации А и
идентификаторами организации Б: каждый роут отвечает 403/404, ни один не отдаёт данные
и ни один не различает «нет прав» и «не существует» (правило `middleware.ts:33-35`
распространяется на организации). Тест роняет CI.

### Шаг 3 — адресаты и виды поручений (ломающая миграция №2, expand/contract)

- **Expand:** `task_assignees` (`task_id`, `user_id`, `state`, `accepted_at`,
  `acknowledged_at`, `done_at`); `tasks.kind`; `tasks.author_id`, `remind_at`,
  `source`, `origin_audio_id`, `declined_reason`. Бэкфилл из `responsible_user_id`.
- Двойная запись, старое поле остаётся.
- Перевод чтений: `routes.ts:38` (notifyTask), `:301` (archive/mine), `:401/410/413`
  (создание), `:453/479` (patch), `:498` (правило «только ответственный двигает»
  становится «любой адресат двигает свою строку»); `scheduled.ts:37, 65, 88` — три
  `JOIN users u ON u.id = t.responsible_user_id`.
- **Contract:** `responsible_user_id` удаляется отдельным релизом.
- `confirm`/`reject` (`routes.ts:555-589`) требуют решения: при `kind='each'` задача
  закрывается по каждому адресату отдельно. См. ADR-3.

**Приёмка шага 3:** `COUNT(*) FROM tasks` = `COUNT(DISTINCT task_id) FROM task_assignees`
после бэкфилла; рассылка на 14 человек имеет 14 независимых состояний; существующая
доска работает без изменений во фронте до contract-релиза.

### Шаг 4 — Telegram-бот, разбор речи, личный слой

- Подключение: `users.telegram_user_id`, `invite_token`, `PENDING`-состояние.
- Разбор: адаптер STT по образцу `Evi/core/app/adapters/`, строгий JSON, обязательный
  переспрос кнопками, `school.json` вне промпта.
- Личный слой: адресат = автор; инициатива только по поручениям другим; потолок
  2 повода в день; `events.type = 'miss'` для `/промах`.
- Тихие часы 20:00–08:00 и воскресенье — в единственной точке отправки.

### Шаг 5 — mini-app

- Экраны Моё / Люди / Календарь / Настройки; вход по `initData` (HMAC-SHA256);
  календарь — представление задач с датой, не канал уведомлений.

## Расширенный тест-план

**Unit.** Разрешение адресата из речи (имя / должность / группа → пользователь или
переспрос); расчёт `remind_at` от `due_at`; `describeOverdue` и `formatOverdue`
(`routes.ts:47-53`, `scheduled.ts:105-112`) при переходе на несколько адресатов;
валидация `initData` по HMAC.

**Integration.** Переход состояния из двух путей даёт одинаковый результат; бэкфилл
сохраняет число задач; дедупликация напоминаний (одно уведомление уходит ровно раз);
`resolveDependency` (`routes.ts:374-386`) не пропускает зависимость между
организациями.

**E2E.** Сценарий спеки целиком: голосовое → переспрос → постановка → «Принял» →
напоминание → закрытие → уведомление автору. Отдельно `kind='ack'`: рассылка на N,
частичное ознакомление, «напомнить всем разом», закрытие директором не дождавшись двоих.

**Изоляция (роняет CI).** Перебор всех роутов Hono токеном чужой организации.

**Observability.** Счётчик отказов отправки в Telegram (сейчас `scheduled.ts:49, 77, 100`
молча делают `continue` — при постоянном сбое напоминания исчезают бесшумно);
счётчик поводов в сутки против потолка 2; доля переспросов, подтверждённых без правок.

## Риски и снятие

| Риск | Снятие |
|---|---|
| Межтенантная утечка через несписочные роуты | Тест перебором роутов, а не списком (шаг 0, усиливается на шаге 2) |
| Форвард-онли миграции D1 без отката | Expand/contract; старое поле живёт до отдельного contract-релиза |
| Внутренний `JOIN` молча теряет задачи без адресата | Инвариант количества проверяется до переключения чтений |
| Второй экземпляр правил доступа (`attachmentForAccess`) | Схлопывается на шаге 0, до появления организаций |
| Молчаливый отказ отправки в Telegram | Счётчик в observability |
| `MCP_USER_ID` как хардкод при нескольких арендаторах | Привязка к организации на шаге 2 |

## Открытые вопросы для Architect и Critic

1. Последовательность: вариант C против A — оправдан ли шаг 0 без видимой функции.
2. ADR-2: отказ от вебхуков в пользу единой точки перехода — не теряется ли будущая
   потребность (внешние интеграции отложены, но не отменены).
3. ADR-3: семантика `confirm`/`reject` при `kind='each'` и `kind='ack'` — задача как
   целое против строки адресата.
