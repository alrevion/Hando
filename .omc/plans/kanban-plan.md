# Рабочий план: внутренняя Kanban-доска (Cloudflare Workers + D1)

Статус: **pending approval** (ожидает утверждения)
Исходная спека: `.omc/specs/deep-interview-kanban.md` (неопределённость 12.5%, PASSED)
Консенсус: черновик Planner -> ревью Architect -> ревью Critic (APPROVE WITH REQUIRED CHANGES) -> правки внесены ниже. Одна итерация; повторный цикл не потребовался (вердикт Critic — конкретные точечные правки, а не отказ от подхода).

## RALPLAN-DR Summary (короткий режим)

**Принципы**
1. Переиспользовать существующую инфраструктуру (`auth-api`) вместо повторного изобретения телефон/OTP-аутентификации.
2. Контроль доступа обеспечивать на уровне API, а не только UI — явное жёсткое требование (Раунд 4).
3. Предпочитать простейший механизм, удовлетворяющий каждому требованию — 5-секундный polling вместо WebSockets/Durable Objects, один Worker вместо разделения на сервисы. Это новое архитектурное решение именно для топологии деплоя этого проекта, принятое ради простоты при небольшом масштабе — само по себе оно не было результатом интервью (интервью решило только polling-vs-realtime, в Раунде 6; спека прямо оставляет "точный поддомен/конфиг wrangler" нерешённым).
4. Никогда не удалять данные жёстко — везде архивация/soft-delete, с полной атрибутируемой историей событий, а не только полями последнего состояния.
5. Оставаться single-tenant/внутренним инструментом — никакого multi-tenant каркаса, никакой SaaS-эластичности.

**Драйверы решений (топ-3)**
1. Жёсткое инфраструктурное ограничение: всё должно работать на Cloudflare Workers + D1.
2. Нужно переиспользовать существующий сервис `auth-api` для телефон/OTP-входа, а не дублировать эту логику.
3. Нужно точно реализовать конкретный жизненный цикл карточки + Telegram-эскалацию — это и есть ценностное предложение продукта.

**Жизнеспособные варианты**

### Вариант A: один Worker, D1, Cron Triggers (рекомендуется)
Один Cloudflare Worker (роутер Hono) отдаёт и API, и статические файлы фронтенда. D1 хранит все данные. Cron Triggers запускают авто-архивацию и проверку дедлайнов раз в 5 минут.

- **Плюсы:** простейший деплой (один `wrangler.jsonc`, один D1 binding), минимум движущихся частей для небольшого внутреннего инструмента с малым объёмом данных. `apps/server` из `Leum` доказывает, что Cloudflare поддерживает совмещённый API+asset origin в этой организации (другой бэкенд — Neon+Durable Objects, не D1 — но та же форма).
- **Минусы:** связывает cron эскалации, роуты авторизации, API и раздачу статики в один деплой/зону поражения. **Исправленная формулировка (и Architect, и Critic независимо отметили, что исходное обоснование было перевёрнуто):** это *не* "существующий паттерн" — проверено по каждому `wrangler.jsonc`/`.toml` в репозитории: каждый D1-сервис (`auth-api`, `email-api`, `push-api`, `telegram-otp-api`, `otp-gateway`, `sms-otp-api`, `Ready/api`) — чистый API-воркер без assets binding, а каждый asset-воркер (`Ijoda/app`, `Ijoda/cabinet` и т.д.) не имеет D1. **Стандартная для организации форма — это как раз разделение** (Вариант B) — `Ready/api` (D1, без assets) + `Ready/Landing` (assets, без D1) — ближайший реальный прецедент, причём CORS там избегается через service binding, а не cross-origin fetch. Вариант A выбран здесь ради простоты при небольшом масштабе именно этого проекта, а не потому что "так принято".

### Вариант B: разделённые Worker'ы (фронтенд / API+cron)
- **Плюсы:** соответствует реально сложившейся конвенции организации (разделение `Ready` на api/Landing). Изолирует зону поражения cron-эскалации от деплоя фронтенда и от авторизации — баг в цикле Telegram-эскалации не может обрушить логин или статический UI, а правка CSS не требует передеплоя cron/auth-бэкенда.
- **Минусы:** удваивает поверхность конфигурации/деплоя (два `wrangler.jsonc`, service binding или настройка CORS) для проекта, явно описанного как небольшой и внутренний, без заявленной потребности в независимом масштабировании или границах владения командами.

**Обоснование отклонения Варианта B:** реальные преимущества Варианта B (соответствие конвенции организации, изоляция зоны поражения) — не надуманные, а настоящие, но Non-Goals спеки прямо исключают multi-tenant/масштабные задачи, для которых изоляция была бы ценна, а это инструмент, который поддерживает один человек. Вариант A принимается на честном основании "проще для этого масштаба", с оговоркой, что если инструмент вырастет по охвату или получит второго мейнтейнера, разделение по Варианту B — естественный следующий шаг (см. Follow-ups).

## Сводка требований

Построить внутренний Kanban-инструмент с входом по телефону/OTP, 3-уровневой ролевой иерархией (creator > super-admin > admin), контролем видимости/доступа по проектам на уровне API, фиксированной 3-колоночной доской с блокировкой редактирования + жизненным циклом архивации/подтверждения/восстановления с полной атрибутируемой историей, и Telegram-ботом, который выводит просроченные задачи на первый план до их решения. Полная детализация — в разделах Goal/Constraints/Acceptance Criteria исходной спеки.

## Модель данных (D1 / SQLite)

- **users**: id, phone (уникальный), name, role (`creator`|`super_admin`|`admin`), created_at
- **projects**: id, name, created_by, created_at, archived_at (nullable — soft-delete; см. Follow-ups, не подтверждено с постановщиком требований)
- **project_memberships**: id, project_id, user_id, created_at
- **tasks**: id, project_id, title, description, responsible_user_id, status (`todo`|`in_progress`|`done`|`archived`), deadline (nullable дата), done_at (nullable — управляет 7-дневной авто-архивацией и расчётом просрочки), telegram_message_id (nullable, текущее "живое" сообщение для этой задачи — см. дизайн Telegram ниже), last_escalated_at (nullable — защита от дублирующей эскалации при повторном срабатывании Cron), created_at, updated_at. **Эта таблица — денормализованный кэш текущего состояния для быстрого рендера доски, а не система учёта "кто что сделал".**
- **events** (только добавление, система учёта атрибуции): id, actor_id (nullable — null означает системное/автоматическое действие, например авто-архивацию), target_type (`task`|`project`|`membership`|`user`), target_id, action (`archived`|`restored`|`confirmed`|`rejected`|`deleted`|`created`|`membership_added`|`membership_removed`|...), comment (nullable — обязателен на уровне API для `restored`), overdue_by (nullable секунды, устанавливается при `confirmed`/`rejected`), created_at. Одна унифицированная таблица покрывает и требование аудита из Раунда 4 (действия с проектами/участниками), и атрибуцию во вкладке "Архив" по задачам (циклы архивация/восстановление/подтверждение/отклонение) — задачу можно заархивировать, восстановить и заархивировать снова, и каждое событие — своя строка, а не перезапись одной колонки.

**Исправление относительно первого черновика:** в первом черновике поля `archived_by/archived_at/restored_comment/confirmed_by/confirmed_at/overdue_by` были однозначными колонками прямо на `tasks`. И Architect, и Critic независимо указали, что это не может представить повторяющиеся циклы (архивация->восстановление->архивация; Готово->отклонение->В работе->Готово->подтверждение могут повторяться по несколько раз согласно спеке, строки 75/89), и поэтому не может удовлетворить собственному критерию спеки, что *все* такие действия атрибутируемы ("кто что сделал") во вкладке "Архив" проекта. Исправлено переносом всего этого в `events`; `tasks` хранит только достаточно денормализованного состояния (`status`, `done_at`), чтобы рендерить доску и знать *текущее* состояние.

**Follow-up (не подтверждено с постановщиком требований):** спека полностью описывает семантику архивации/восстановления на уровне задач, но про удаление проектов говорит лишь "super-admin/creator удаляют проекты", не раскрывая деталей. Этот план предполагает soft-delete (устанавливается `archived_at`, проект скрывается из сайдбара, задачи остаются видимы через вкладку "Архив" проекта), что согласуется с принципом "никогда не удалять жёстко" — **и уточняет каскад, отсутствие которого отметили Architect/Critic: задачи в работе у soft-deleted проекта исключаются из цикла эскалации** (больше никаких пингов в Telegram по проекту, с которым уже никто не может работать), оставаясь при этом видимыми для `creator`/`super-admin` через "Архив". Это предположение нужно подтвердить до или во время реализации.

## Поток авторизации (исправлено)

Проверено на реальном сервисе `auth-api` (`apps/platform/auth-api/routes/auth.ts`): `/auth/verify` вызывает `getOrCreateUser` и выдаёт сессию для *любого* корректного OTP — у auth-api нет понятия "этому телефону нельзя входить", так что этот гейт целиком на стороне Kanban. Первый черновик вызывал `/auth/login` (отправка OTP) безусловно и проверял таблицу `users` Kanban только на этапе verify — то есть незарегистрированный/произвольный номер всё равно получал бы настоящий OTP до отклонения.

**Исправленный поток**, зеркалирующий собственный прецедент кабинета Ijoda (гейт `staffAllowed()` перед `/auth/login`, `Ijoda/cabinet/supabase/functions/auth-login/index.ts:95`):
1. Пользователь вводит номер телефона.
2. Worker Kanban **сначала** проверяет свою таблицу `users` на этот номер. Не найдено -> немедленный отказ ("телефон не зарегистрирован"), OTP не отправляется, вызов к auth-api не делается.
3. Найдено -> вызов auth-api `/auth/login` для отправки OTP, затем `/auth/verify` для подтверждения.
4. При успехе выдаётся собственный токен сессии Kanban (подписанная cookie/JWT) с `user_id` + `role`.
5. **Актуальность сессии:** поскольку у stateless-токена нет пути отзыва при понижении роли или удалении пользователя, использовать короткий TTL (например, 15-30 минут) и перепроверять текущую строку пользователя (существование + роль) при каждом действии повышенной роли (всё, что доступно только `super_admin`/`creator`) — это переиспользует тот же round-trip к D1, который `requireProjectAccess` и так делает для проверки членства `admin`, просто расширенный для перепроверки роли у старших уровней.

## Шаги реализации

1. **Каркас** (корень репозитория: `api/` для Worker'а, `frontend/` для React-приложения, единый `wrangler.jsonc`, связывающий D1 и собранный фронтенд как assets — этот репозиторий, `apps/systems/business/Kanban`, уже *является* корнем проекта, аналогично тому, как `Ijoda` размещает свои под-приложения как соседей в одном репозитории). D1-миграции по схеме выше.
2. **Интеграция авторизации** (`api/src/auth.ts`): исправленный поток "сначала проверка -> потом OTP" описанный выше.
3. **Middleware контроля доступа** (`api/src/middleware/access.ts`): `requireProjectAccess(userId, projectId)` — `super_admin`/`creator` проходят всегда; `admin` проходит только при наличии строки в `project_memberships`. Возвращать одинаковый 403 и для не-участника, и для несуществующего проекта/задачи (чтобы не палить существование через разные коды ошибок). Компаньон `requireRole(userId, [...roles])` для оси "какая роль что может" (удаление/подтверждение/создание super_admin), тестируемый изолированно так же.
4. **CRUD пользователей/проектов/участников** (`api/src/routes/{users,projects,memberships}.ts`): каждое изменяющее действие пишет строку в `events` (актор, действие, цель).
5. **CRUD и жизненный цикл задач** (`api/src/routes/tasks.ts`): создание/редактирование только пока `status = todo`; эндпоинт переноса между колонками обеспечивает блокировку редактирования; удаление доступно только `super_admin`/`creator` (устанавливает `status = archived`, пишет строку в `events` с `action = deleted`); эндпоинт восстановления требует `comment` (400 при отсутствии), возвращает `status`, пишет строку в `events` с `action = restored`.
6. **Поток подтверждения**: `POST /tasks/:id/confirm` (только `super_admin`/`creator`) — считает `overdue_by`, если применимо, пишет строку в `events` (`action = confirmed`). `POST /tasks/:id/reject` — возвращает `status = in_progress`, дедлайн не трогается, пишет строку в `events` (`action = rejected`).
7. **Запланированные задания** (`api/src/scheduled.ts`, Cron Trigger, каждые 5 минут): (a) авто-архивация — `status = done` и `done_at` старше 7 дней -> `status = archived`, строка в `events` с `actor_id = null` (система); (b) проверка просроченных дедлайнов — для `status = in_progress` с прошедшим `deadline` **и чей проект не в soft-delete**, запускается цикл send-new/delete-old в Telegram (см. дизайн ниже); защита через `last_escalated_at` (пропуск, если с последней эскалации по этой задаче прошло меньше ~4 минут), чтобы двойное срабатывание Cron не отправило дублирующее сообщение до удаления предыдущего.
8. **Интеграция Telegram-бота** (`api/src/telegram.ts`), **финальный дизайн** (send-new + delete-old, выбран постановщиком требований вместо исходной идеи с массивом/массовым удалением и альтернативы с редактированием на месте): хранить единственный `telegram_message_id` на задачу — в любой момент существует не больше одного "живого" сообщения для этой задачи. При входе в `in_progress` — `sendMessage` с объявлением ответственного + дедлайна, сохранить полученный id. На каждом такте эскалации после дедлайна: `sendMessage` **новое** тегированное сообщение ("ВЫ ПРОСРОЧИЛИ ДЕДЛАЙН" + обновлённая длительность просрочки), затем `deleteMessage` по **предыдущему** сохранённому id, затем сохранить новый id. При достижении `done` — удалить последнее сохранённое сообщение. Поскольку удаляемое сообщение всегда из *предыдущего* 5-минутного такта, оно всегда далеко внутри окна ~48 часов Telegram на удаление, независимо от того, сколько задача остаётся просроченной — проблема массива/48 часов структурно не может возникнуть, а не просто не возникает в обычном случае. Это также сохраняет настоящий пуш-звук на каждой эскалации (свежее сообщение, а не тихое редактирование) — то, ради чего изначально и просился вариант "каждые 5 минут".
9. **Фронтенд** (`frontend/`, React + Vite + TS + Tailwind, как у Ijoda): экран входа (телефон + OTP), сайдбар (назначенные/все проекты по роли), вид доски (3 фиксированные колонки, с учётом блокировки редактирования), вкладка "Архив" по проекту (`super_admin`/`creator`, на основе `events`, join с `tasks`) и личная вкладка "Архив" (`admin`, отфильтрована на собственные завершённые задачи), 5-секундный polling на виде доски.
10. **Деплой**: `wrangler deploy` из корня репозитория, по существующему паттерну Alrevion (поддомен + D1 + секреты `AUTH_API_KEY` и `TELEGRAM_BOT_TOKEN`).

## Критерии приёмки

Унаследованы из раздела Acceptance Criteria исходной спеки (15 проверяемых критериев — см. `.omc/specs/deep-interview-kanban.md#acceptance-criteria`), с двумя, теперь явно проверяемыми благодаря исправлению схемы выше:
- Критерий "атрибутируемо конкретному пользователю и времени" (спека, строка 79) удовлетворяется через таблицу `events`, включая повторяющиеся циклы архивация/восстановление или отклонение/подтверждение (а не только последний).
- Критерий "сообщения эскалации удаляются при завершении" (спека, строка 77) удовлетворяется безусловно (не только в пределах 48 часов) благодаря дизайну send-new/delete-old — на удаление всегда ожидает не больше одного сообщения, и оно всегда свежее.

## Риски и меры по их снижению

| Риск | Мера |
|------|------|
| Утечка данных между проектами через API (жёсткое требование Раунда 4) | Единая пара middleware `requireProjectAccess` + `requireRole`, применяемая к каждому роуту; отдельный набор тестов, проверяющий 403 и для доступа не-участника, и для действий, требующих определённой роли |
| Повторяющиеся циклы жизненного цикла задачи перезаписывают атрибуцию | Таблица `events` только на добавление, вместо однозначных колонок на `tasks` |
| Рост числа сообщений Telegram / окно удаления 48ч / лимиты частоты | Дизайн send-new/delete-old — не больше одного сообщения на задачу в любой момент; удаляемое сообщение всегда из предыдущего такта, никогда не бывает достаточно старым, чтобы упереться в окно 48ч |
| Сессия остаётся действительной после удаления/понижения роли | Короткий TTL + перепроверка роли/существования при действиях повышенной роли |
| Незарегистрированные номера телефонов вызывают реальные OTP | Проверка существования в `users` до вызова `/auth/login` в auth-api, по аналогии с гейтом `staffAllowed()` в Ijoda |
| Двойное срабатывание Cron дублирует действия эскалации | Защита `last_escalated_at` на `tasks` — повторное срабатывание в пределах того же ~5-минутного окна ничего не делает (send-new/delete-old, в отличие от редактирования, не идемпотентен сам по себе, поэтому эта защита обязательна, а не опциональна) |
| Задачи soft-deleted проекта эскалируют бесконечно | Цикл эскалации исключает задачи, чей проект имеет установленный `archived_at` |
| Зависимость от доступности внешнего `auth-api` | Принято как есть — соответствует существующему паттерну Ijoda; дополнительных мер для MVP не предусмотрено |
| Лимиты чтения/записи бесплатного тарифа D1 | Низкий риск при явно небольшом внутреннем объёме данных; пересмотреть при росте использования |

## Шаги проверки

1. Юнит-тесты для `requireProjectAccess` и `requireRole` (участник/не-участник, верная/неверная роль, единообразный 403 для несуществующих id).
2. Интеграционный тест: полный жизненный цикл задачи create(todo)->edit->перенос в in_progress (редактирование теперь заблокировано)->done->confirm (вовремя) и второй прогон ->reject (возврат в in_progress, дедлайн не меняется)->в итоге позднее confirm (`overdue_by` > 0) — с проверкой, что каждый переход пишет верную строку в `events`.
3. Интеграционный тест: архивация через удаление (только super_admin; попытка admin -> 403) -> восстановление требует comment (без него -> 400) -> архивация снова — проверить, что вид "Архив" проекта показывает **оба** события архивации отдельно (а не одну перезаписанную строку).
4. Интеграционный тест: проверка авторизации отклоняет незарегистрированный телефон без единого вызова `/auth/login` в auth-api (замокать/отследить исходящий вызов).
5. Ручное QA на реальной тестовой группе в Telegram: бот постит сообщение при входе в `in_progress`; после просрочки на каждом 5-минутном такте постит новое тегированное сообщение и удаляет предыдущее (проверить, что "живое" сообщение всегда одно); имитация двойного срабатывания Cron в пределах защитного окна ничего лишнего не отправляет; при Done финальное сообщение удаляется — проверить отсутствие оставшихся сообщений бота в группе после этого.
6. Ручное QA: авто-архивация после 7 дней в `done` (имитировать сдвигом `done_at` назад); просроченная задача soft-deleted проекта перестаёт эскалировать.
7. Ручное QA: вид доски отражает изменение другого admin'а в пределах ~5 секунд без ручной перезагрузки.

## ADR

**Решение:** построить единый Cloudflare Worker (Hono) + D1 + Cron Triggers для внутреннего Kanban-инструмента, переиспользуя существующий сервис `auth-api` для входа по телефону/OTP, с таблицей `events` только на добавление для полной атрибуции жизненного цикла и дизайном Telegram-эскалации send-new/delete-old.

**Драйверы:** должно работать на Cloudflare Workers + D1; должно переиспользовать `auth-api`, а не дублировать логику OTP; должно точно реализовывать поток ответственности за дедлайны (основная ценность продукта) без неограниченного роста сообщений и без неатрибутируемой истории.

**Рассмотренные альтернативы:**
- Разделённые Worker'ы (фронтенд / API+cron), соответствующие реальной конвенции организации (разделение `Ready` на api/Landing) — отклонено для масштаба этого проекта не потому что паттерн хуже, а потому что дополнительная поверхность деплоя/CORS-или-service-binding не оправдана инструментом, который поддерживает один человек, без потребности в изоляции/масштабировании.
- Однозначные колонки последнего состояния на `tasks` для атрибуции архивации/восстановления/подтверждения — отклонено, потому что собственная машина состояний спеки допускает повторяющиеся циклы (архивация/восстановление, отклонение/подтверждение), которые однозначные колонки молча перезаписывают, нарушая критерий приёмки "атрибутируемо конкретному пользователю".
- Растущий массив id сообщений Telegram с массовым удалением при завершении — отклонено, потому что он неограничен, упирается в окно удаления ~48ч Telegram на долго просроченных задачах (постоянно висящие сообщения) и рискует лимитами частоты на группу.
- Редактирование на месте единственного сообщения (предложено во время ревью плана) — рассмотрено, но отклонено постановщиком требований: редактирование не гарантированно вызывает пуш-звук при каждой эскалации, как это делает свежее сообщение, а именно в этом и был смысл "каждые 5 минут".

**Почему выбрано:** Вариант A (единый Worker) — простейшая форма, удовлетворяющая всем жёстким ограничениям при реальном масштабе этого проекта (одна компания, малый объём данных, отсутствие заявленной потребности в мультикомандности/масштабировании); таблица `events` и дизайн Telegram send-new/delete-old — минимальные исправления, необходимые, чтобы собственные заявленные критерии приёмки плана были действительно выполнимы, без добавления незапрошенной инфраструктуры. Send-new/delete-old выбран вместо редактирования на месте именно потому, что сохраняет настоящий пуш-звук на каждой эскалации, при этом структурно избегая проблемы 48ч/роста (удаляемое сообщение всегда из непосредственно предыдущего такта).

**Последствия:** cron, авторизация, API и раздача статики Worker'а делят один деплой и одну зону поражения — приемлемо при таком масштабе, но естественный следующий шаг, если инструмент вырастет (больше проектов/пользователей, второй мейнтейнер, потребность развивать фронтенд независимо от бэкенда) — разделить на Worker для API+cron и отдельный статический Worker/Pages-проект, по аналогии с `Ready`. Таблица `events` будет расти без ограничений (только добавление); при таком объёме данных это не проблема на годы вперёд, но политика чистки/архивации в будущем — разумный follow-up, когда появятся реальные данные об использовании.

**Follow-ups (открытые пункты, требующие быстрого подтверждения от постановщика требований, не блокируют начало разработки):**
1. Подтвердить, что soft-delete проекта — это именно та семантика, которая нужна (план это предполагает), и что исключение задач soft-deleted проекта из эскалации — правильный каскад.
2. Пересмотреть топологию Worker'ов (единый vs разделённый), если охват инструмента вырастет или появится второй мейнтейнер.

**Решено в ходе ревью плана:** дизайн Telegram-эскалации изначально был черновиком с редактированием на месте, чтобы обойти окно удаления 48ч; постановщик требований выбрал вместо этого send-new/delete-old (новое тегированное сообщение на каждом такте, удаляется только непосредственно предыдущее) — это сохраняет поведение "пристыдить пингом" из исходного интервью, при этом структурно избегая проблемы 48ч/роста, поскольку удаляемое сообщение никогда не старше одного интервала эскалации.

## Changelog (улучшения, внесённые по итогам ревью Architect + Critic)

- Исправлено обоснование Вариант A/B: убрано ложное утверждение "соответствует существующему паттерну Ijoda" (проверено — ни один существующий сервис не совмещает D1 + assets в одном Worker'е), Варианту B отдано должное как реальной конвенции организации, рекомендация Варианта A переобоснована через простоту-при-таком-масштабе.
- Исправлена неверная атрибуция выбора единого Worker'а к решению интервью Раунда 6 (Раунд 6 решал только polling vs realtime; топология деплоя на интервью не обсуждалась).
- Однозначные колонки `archived_by/archived_at/restored_comment/confirmed_by/confirmed_at/overdue_by` на `tasks` заменены таблицей `events` только на добавление — исправлен пробел, ломающий критерий приёмки (повторяющиеся циклы архивация/восстановление или отклонение/подтверждение перезаписывали бы предыдущую атрибуцию).
- Эскалация в Telegram переработана из растущего массива сообщений + массового удаления в send-new/delete-old с единственным "живым" сообщением — исправлен риск неограниченного роста / окна удаления 48 часов / лимитов частоты (при сохранении настоящего пуш-звука на каждой эскалации, по явному предпочтению постановщика требований вместо тихого редактирования на месте) и вытекающая из этого невозможность удовлетворить критерий "сообщения удаляются при завершении" для долго просроченных задач. Добавлена защита `last_escalated_at`, поскольку этот дизайн, в отличие от редактирования на месте, не идемпотентен сам по себе против двойного срабатывания Cron.
- Поток авторизации переупорядочен: проверка существования в `users` теперь идёт до отправки OTP через auth-api (раньше реальный OTP отправлялся на незарегистрированные номера до отказа при verify), по аналогии с процитированным прецедентом Ijoda.

- Уточнён ранее не описанный каскад: задачи в работе у soft-deleted проекта исключаются из цикла эскалации.
